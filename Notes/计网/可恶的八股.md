### 非对称加密？

搞俩大质数 $p,q$，算 $n=p·q$，此时 $\phi(n)=(p-1)(q-1)$
那我现在选定一个数 $e$ ，保证 $e$ 和 $\phi(n)$ 互质
费马小定理算 $e$ 模 $\phi(n)$ 意义下的乘法逆元 $d$
此时 $(n,e)$ 就是公钥，$(n,d)$ 就是私钥
因为别人拿到 $n$ 很难快速分解出 $p$ 和 $q$ 来，也就没法算 $\phi(n)$ ，也就没法算乘法逆元 $d$

### HTTPS

我说 `HTTPS=HTTP+校验和+机构认证+加密通信`

注册了 HTTPS 的服务器要找 CA 认证，CA 搞一份证书，用自己的密钥加密证书哈希值
当连接的时候，客户端要求 TLS 握手，发了一个随机数 Client Random
服务器把证书和另一个随机数 Server Random 发给客户端
客户端收到数字证书，自己算一遍哈希值，再解密一下 CA 加密的哈希值，看到一样，证明服务器确实被 CA 认证了
于是客户端搞了一个随机数 pre-master key，用证书里边服务器的公钥加密以后发回去，并用这个随机数和前边俩随机数作为 seed 生成一个真正的对称密钥
服务器用自己的私钥解密以后，也用相同的随机算法生成相同的对称密钥
他俩用这个密钥发个 ok 了
就可以对称加密了

然后他俩发信息的时候，会用密钥作为参数算一个校验和，可以起到防伪和保证数据有效的作用~

在某些对安全性要求较高的场景下可能会用双向认证，也就是服务端也需要认证客户端的证书，并且检查是否有效，实际上是维护了一个可以访问我的白名单，可以防止代理人攻击。

但是现在的 TLS 1.3 已经变成了 1-RTT，它的主要区别是
一开始，客户端生成一个临时的公私钥对，并把公钥和一个随机数 Client Random 发给服务端
服务端也生成临时的公私钥对，并把公钥和另一个随机数 ServerRandom ，以及证书发给客户端

这里我要介绍一下 ECDH 算法
它是去计算 $A=g^a\mod p$，A 是公钥，a 是私钥
我们以客户端为例，我现在知道了 a 和 B，我可以去计算 $S=g^{ab}=B^a$，服务端也一样，那么双方现在就能算出来 S 作为 pre-master key 了

之后就都一样了，生成一个真正的密钥，然后开始加密通话

### HTTP 2

默认开启 HTTPS，压缩头部（维护一个特殊编码格式的 map ），二进制格式，并发传输（维护 ID，到达的顺序就不重要了），服务器推送
但是由于 HTTP 2 还是基于 TCP 的，所以一旦某个包丢了，还是会阻塞队列。

### HTTP 3

改成 UDP 了，但是引入了一个 QUIC 协议做可靠性传输

QUIC 保证了当一个流丢包的时候只阻塞这个流
QUIC 减少了握手次数，三次握手就可以同时建立连接和 TLS 认证（因为以前基于 TCP 的时候得走其他库的实现，不好改）
QUIC 还弃用了源/目标 ip、端口的设置，因为网络环境改变的时候需要重新握手，而是维护了连接 id，消除了重连的成本

### 重传机制？

超时重传：一段时间内没收到 ACK 就重传
快速重传：连续三次收到相同的 ACK 就重传
SACK：在 ACK 包里维护一个 SACK，用于记录缺失段后边哪些数据收到了
D-SACK：维护一个 D-SACK，用于记录哪些包被重复传过来了，方便进行诊断是谁的原因
回退 N 帧：出错双方都回退 N 帧重新传输

### 流量控制？

流量控制主要是滑动窗口控制的。

窗口就是允许发送方在没收到 ACK 之前连续发送的最大字节数，需要维护发送窗口和接收窗口

接收窗口取决于接收方的缓冲区大小，当发 ACK 包的时候会顺带通告发送方还剩多大（有的时候也会特地发 ACK 包通告窗口大小）
发送窗口则是 $\min(接收窗口，拥塞窗口)$

当发送窗口归零的时候，发送方会定期试探接收方，以避免关键的窗口变大消息丢失，产生死锁。
当接收方需要减小缓冲区大小的时候，需要先通告发送方窗口缩小，等发送方适应以后再真正减小缓冲区，以免丢包的情况产生

当接收方接收能力很差，窗口很小的时候，就会导致为了发很少的消息而发送一整个大包，叫糊涂窗口综合征。要解决这个问题，一般是接收方在发现窗口比较小的时候直接通告窗口大小为 0 ，等扩大到一定值再通告，并且发送方用 Nagle 算法

### 拥塞控制？

拥塞控制是避免网络压力过大用的。

维护了一个拥塞窗口 cwnd，当网络无压力的时候会扩张，有压力的时候会缩小。

慢启动：每次收 ACK 包都会使得 cwnd 的大小+1，直到达到慢启动门限。（所以每轮窗口大小都会乘以二）
拥塞避免算法：到达慢启动门限以后，每次收 ACK 包都会使 cwnd 大小增加 1/cwnd。（也就是每轮窗口大小+1）

当拥塞发生时，会产生重传

超时重传：门限变成 cwnd/2，cwnd 重置
快速重传：门限变成 cwnd/2，cwnd 变成门限+3，进入快速恢复

快速恢复：重传之前的数据包，如果收到重复 ACK 就让 cwnd 大小+1，如果收到新的 ACK，就让 cwnd 变成门限，回到拥塞避免模式

### 什么情况下 SYN 会被丢弃？

1. 当全连接队列满时，会直接丢弃 SYN 包拒绝握手
2. 当半连接队列满时，也会丢弃，但是如果开启了 cookies 功能，会计算一个 cookie 返回给客户端，当客户端返回 ACK 报文时，如果是合法的，就建立连接。
3. 为了防御 DDos 攻击主动丢弃，或者防火墙过滤

### 已经建立连接的 TCP 收到 SYN 包会怎样？

就是说客户端宕机了，然后重启以后重新建立连接

第一种情况，端口号不一致
服务器会当成全新连接来回一个 SYN-ACK 包，但是客户端那边认为没有这个连接就回了 RST

第二种情况，端口号一致
客户端发送 SYN 包以后，服务端回复的会进行一次 challenge ACK： SYN-ACK 包中 ACK 信息可能并不是 SYN 包里的 seq+1，导致客户端发现不对劲，就发了 RST

### 握手挥手丢包会怎么样

首先要知道一个东西叫指数退避，比如我发一个 SYN 包没收到回报，我会隔 1、2、4、8、16... 个单位时间重发 SYN，到一定次数以后就不试了，拉倒吧
其次，要知道 ACK 包是不会重发的。

握手
1. 第一个包丢了：多试几次不行就 close 了
2. 第二个包丢了：也会多试几次，而且由于第一个包没收到回报也会重试，所以这里会多试很多次。（知道会重传就行）
3. 第三个包丢了：ACK 包不会重传，但是由于第二个包没收到回报了会重传，所以 ACK 包看起来也会重传多次。然后 A 以为自己建立连接了，后面再发心跳包或者发信收到 RST 时候就结束了。

挥手
1. 第一个包丢了：多试几次不行就 close 了，连接自然消亡（见握手 3）
2. 第二个包丢了：ACK 包不会重传，但第一个包没收到回报 A 会多发几次。但是 B 并不知道自己的 ACK 没到达，所以还是会等自己这边调用 close，也就是依然处于 CLOSE_WAIT 状态。A 那边连接自然消亡了
3. 第三个包丢了：多试几次没回报自己这边 close 了，对面那边也会因为 FIN_WAIT_2 时间耗尽自然 close
4. 第四个包丢了：ACK 包不会重传，但第三个包没收到回报 B 会不断重传，而且由于不停收 FIN，让我 TIME_WAIT 状态计时器不停重置。对方不再重试对方会 close，我这边 TIME_WAIT 时间耗尽也会 close

### 复用 TCP 连接可能的后果？

由于它是直接打断了 TIME_WAIT 状态，所以 TIME_WAIT 的那些好处都会炸。

比如说，服务端那边还在 LAST_ACK 状态，你给他发了 SYN，他就会 challenge ACK 你，你回报 RST，就连接失败了
或者说，早先的 RST 包由于网络延迟在建立连接以后才到达，由于 RST 包不带时间戳，所以直接会把你这个连接杀掉
