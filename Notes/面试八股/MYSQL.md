### 联合索引？

当我搞了一个 (a, b) 的联合索引的时候相当于是一个 `map<array<int,2>,int>`，是按字典序来排的。
所以当你查 a=1 and b=1 的时候会走这个联合索引二分
但是查 a>1 and b=1 的时候却只有 a 走了，是因为因为为每个不同的 a 值单独做二分查找和跳转的随机 I/O 开销比直接遍历大，所以不如找到 a 的边界然后直接暴力扫

同时还需要注意的是，如果你写 a>=1 and b=1，在 a=1 这个键确实存在的条件下，b 索引也会有用（为什么>不可以？你二分的时候返回的肯定是第一个 a>1 的地方，那不就是 b 没用到吗）

就是不走索引了

### 事务的 ACID 是什么？如何保证？

A 原子性，如果出错就回滚
C 一致性，执行前后数据的正确性需要有保证
I 隔离性，并行的事务互不干扰
D 持久性，事务结束后对数据的修改是持久的

A：undo log
C：通过其他三个性质来保证的
I：MVCC/锁
D：redo log

### NOSQL？

大概就是指 Redis 那样的非关系型数据库

SQL 以严格的数据结构、关系约束和 ACID 事务为核心，而 NoSQL 通过放宽这些规则来换取水平扩展能力和灵活的数据模型。

1. SQL 表有固定的列和类型，NoSQL 通常允许动态列（同一行的列可以不同）。
2. SQL 强调 ACID 强事务，NoSQL 多数为最终一致性（BASE），部分支持轻量级事务。
3. SQL 支持复杂 JOIN，NoSQL 通常不支持或不鼓励。
4. SQL 主要为垂直扩展（或较复杂的分片），NoSQL 设计原生支持水平扩展。

就是说，非关系型数据库里的数据可以是动态的，而且是没有关系的，你没法去描述一个人的 id 在另一个表上的表现这样，但是正因如此，它的设计就可以更加偏向于提高效率或者提供更灵活的存储方式，也就是：放弃关系约束，换取效率与灵活

### 范式

1. 第一范式
字段有原子性，不可再分，比如你不能搞一列放选课列表（课程 1，课程 2，课程 3...）
2. 第二范式
满足 1 NF 的同时，不能有部分函数依赖
也就是说你如果有联合主键的情况下，不能只通过部分主键就能推出一列的信息，冗余了
3. 第三范式
满足 2 NF 的同时，非主键列之间不能存在依赖关系
也就是说不能有传递关系，比如 A->B 的同时 B->C 否则你要是想改一行的 B 信息的话你还得顺手把 C 给改了，而且也冗余了
4. BCNF
满足 3 NF 的同时，要求主属性之间也不能有依赖关系

### 数据引擎

1. InnoDB
默认的存储引擎。支持 ACID 事务、行级锁并发控制、使用聚簇索引（读取效率高，但是空间复杂度较高），日志，功能全面的全能型选手
2. MyISAM
不支持 ACID 事务，表级锁并发控制，索引和数据分离，也没有外键约束之类的东西，结构简单，所以空间复杂度低
3. Memory
就是个内存数据库，乏善可陈。

### 索引分类？

按数据结构：B+索引、hash 索引、full-text 索引 (专门为文本内容设计的、用于“关键词匹配”而非“字面模式匹配”的索引)
按物理存储：聚簇索引、二级索引

### 索引下推？

比如建了联合索引 （A, B）的情况下
你去找 A=10 and B>20
那你第一次二分确定了 A=10 的开头以后，向右遍历的时候不会每次查表，而是直接去查当前联合索引里 B 的信息，确定是以后再回表

### 覆盖索引？

在索引下推的基础上，如果你只 SELECT B，那么根本不需要回表

### 当你用一个 VARCHAR 存数字，然后查询 x>10，会发生什么？

那你会把 VARCHAR 做一个隐式转换成数字。

即使你建了索引，他也是字典序索引，所以根本不会走索引，而且还有隐式转换的开销。

### 并发事务问题？

脏读、不可重复读、幻读

脏读：读到别的事务改到一半的东西
不可重复读：多次读同一个数据，前后不一致
幻读：前后两次读到符合条件的记录数不一样

如何解决呢？

1. 锁
可以用行级锁和表级锁来解决，其中行级锁只有 InnoDB 支持
2. 事务隔离
包括读未提交、读提交、可重复读、串行化，可以控制事务之间的隔离级别
3. MVCC
保存不同版本的快照，读数据的时候根据隔离级别来选择合适的版本来读

### 事务隔离级别

1. 读未提交，指一个事务还没提交时，它做的变更就能被其他事务看到 
2. 读提交，指一个事务提交之后，它做的变更才能被其他事务看到 
3. 可重复读，指一个事务执行过程中看到的数据，一直跟这个事务启动时看到的数据是一致的，MySQL InnoDB 引擎的默认隔离级别
4. 串行化，会对记录加上读写锁，在多个事务对这条记录进行读写操作时，如果发生了读写冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行；


读未提交：可能发生脏读、不可重复读、幻读
读提交：可能发生不可重复读、幻读
可重复读：可能发生幻读（可能看到新插入的行）
串行化：什么都不会发生。

实现方法：
读未提交：只有写操作加行级锁
读提交：每个 SELECT 操作都生成一个快照，只能看到已提交数据
可重复读：第一次 SELECT 操作的时候生成一个快照，看不到其他人提交的东西
串行化：相当于放弃并发

Mysql 会用间隙锁防止可重复读的幻读问题

### 锁

全局锁：用于全库备份用的，全数据库都会只读
表级锁：分为元数据锁（保证读写正确），自增锁（维护 AUTO_INCREMENT 正常工作），意向锁（协调行锁和表锁）
行级锁：最细的锁，冲突概率低，但是开销大，可能死锁

记录锁：锁住的是一条记录本身
间隙锁：锁定索引的区间，防止其他事务向这个区间插入记录
Next-key Lock：记录锁+间隙锁，解决幻读问题

### 日志
1. Redo 日志
保证持久性，类似于 redis 的那种 AOF，防止 buffer pool 写回不及时崩溃造成数据丢失的
2. Undo 日志
保证原子性，如果运行失败就回滚所有操作
3. Bin 日志
二进制日志，用于主从复制和数据备份
4. Relay 日志
slave 拷贝 master 的 bin 日志以后在本地生成的
5. 慢查询日志
专门用来记录什么查询慢了

### Double Write

在你需要把一批脏页刷回磁盘的时候，要把他们先刷到磁盘上的一个 Double Write Buffer 上，再从 Double Write Buffer刷到磁盘的数据文件里。

这样当你服务器突然掉电的时候，部分数据文件可能是写了一半的损坏状态，mysql 检查到 checksum 不对，就会去看 double write buffer 尝试修复损坏页。然后才去看 redo log 前滚操作。

### 分库分表

字面意义。有水平和垂直两种分法，水平的话就是模以后映射一下，垂直则是按照不同功能去切分。

### MVCC 是如何实现的？

会给每条数据维护一个版本链，然后在生成 readview 之后，访问某个数据的时候根据生成快照时的版本信息，沿着版本链回溯，直到找到一个可见的版本。

### 为什么一个表记录不推荐多于 2000 w

多于 2000 w 会导致 B+树需要第四层。

会导致 filesort 需要借助磁盘进行，而且 cache 命中率大幅下降。
